## 1. 日常更新 dev

```bash
# 有新增 migration 時先套用（已套用過的會自動略過）
cd api && npm run db:migrate:dev

# build（prod 模式壓縮）＋ 部署
cd .. && npm run deploy:dev
```

部署後若首頁或 `/expand-life/admin/` 短暫回 404 或舊內容，通常是剛生效的空窗，幾秒後重試即可。公開 API 有 60 秒邊緣快取，後台改的內容最慢約 1 分鐘出現在前台。

## 2. prod 首次上線

### 2.1 建立資源並填回設定

```bash
npx wrangler d1 create paa-ur-db
npx wrangler kv namespace create paa-ur-kv-prod
npx wrangler r2 bucket create paa-ur-files
```

把輸出的 D1 `database_id` 與 KV `id` 填進 `api/wrangler.jsonc` 的 `env.prod`（取代全 0 佔位值），並更新檔頭註解與 `api/README.md` 的資源表。

### 2.2 套用 schema

```bash
npm run db:migrate:prod
```

會依序套用：

| migration | 內容 |
|---|---|
| `0001_init` | 資料表 |
| `0002_home_intro` | 首頁簡介的預設內容 |
| `0003_county_revision` | 頁面（計畫說明、補助辦法、申請流程、聯絡窗口）初稿、常見問答五類 26 題初稿、公告分類「宣導資訊」、檔案分類「說明會簡報」「宣傳手冊／摺頁」、線上諮詢設定、`inquiries` 資料表 |

### 2.4 建立 prod 管理員（臨時密碼）

```bash
PPW=$(openssl rand -hex 8)
PHASH=$(node scripts/hash-password.mjs "$PPW")
cat > /tmp/paa-ur-admin.sql <<EOF
INSERT INTO admin_users (username,password_hash,name,role,is_active)
VALUES ('admin','$PHASH','管理員','superadmin',1);
EOF
npx wrangler d1 execute paa-ur-db --remote --env prod --file=/tmp/paa-ur-admin.sql
rm -f /tmp/paa-ur-admin.sql
echo "PROD admin = admin / $PPW   ← 記下，首登後到右上角「變更密碼」修改"
```

### 2.5（建議）上線前閘門

內容還沒準備好之前，可以讓 prod 全站要求帳密，避免半成品被看到或被搜尋引擎收錄：

```bash
npx wrangler secret put BASIC_AUTH_USER --env prod
npx wrangler secret put BASIC_AUTH_PASS --env prod
```

正式開放時把兩個 secret 刪掉即可，不需重新部署：

```bash
npx wrangler secret delete BASIC_AUTH_USER --env prod
npx wrangler secret delete BASIC_AUTH_PASS --env prod
```

### 2.6 部署

```bash
cd .. && npm run deploy:prod
```

## 3. 驗證

```bash
B=https://www.paa.org.tw/expand-life      # dev：https://dev.paa.org.tw/expand-life
curl -s -o /dev/null -w "front %{http_code}\n" "$B/"
curl -s -o /dev/null -w "noslash %{http_code} → %{redirect_url}\n" "$B"   # 應 301 到 $B/
curl -s "$B/api/health"; echo                 # env 應為 prod（dev 為 dev）；回 paa-api 而非 paa-ur-api 代表 Route 沒生效
curl -s "$B/api/home" | head -c 300; echo     # hero、intro
curl -s -o /dev/null -w "admin %{http_code}\n" "$B/admin/"
curl -s -D - -o /dev/null "$B/" | grep -i robots   # dev 應有 noindex；prod 不應有
curl -s "${B%/expand-life}/robots.txt"             # 公會網站的 robots.txt 應含 /expand-life/sitemap.xml
```

人工檢查：首頁主視覺與快速入口、計畫介紹三頁、最新公告、資料下載、常見問答（搜尋與展開）、線上諮詢、聯絡我們；公告內文與附件下載；後台各模組（含頁面、常見問答、設定）可登入維護。手機寬度也要看一次（主選單在 1020px 以下改為漢堡選單，站名較長會換行）。

社群分享預覽：把網址貼到 Facebook 分享偵錯工具或 LINE 對話，確認出現主視覺 OG 圖。

**重設管理員密碼**（忘記密碼時；dev 把 `paa-ur-db`／`prod` 換成 `paa-ur-db-dev`／`dev`）：

```bash
NEW=$(node scripts/hash-password.mjs '新密碼')
npx wrangler d1 execute paa-ur-db --remote --env prod \
  --command "UPDATE admin_users SET password_hash='$NEW', token_version=token_version+1 WHERE username='admin';"
```

## 4. 上線前後的安全性收尾

1. **Turnstile（登入人機驗證）**：與公會網站（paa-web）共用同一個 widget，site key 已填在 `api/src/index.ts` 的 `TURNSTILE_SITE_KEY`。啟用時把**與 paa-web 相同的 secret** 設進來：`npx wrangler secret put TURNSTILE_SECRET --env dev`、`--env prod`。輪替 secret 時兩站都要更新；workers.dev 網址不在 widget 的 Hostnames 內，啟用後要從 `dev.paa.org.tw/expand-life/admin/` 登入。**順序很重要：site key 要先部署，再設 secret。** 後端只看 secret：有 secret 就要求驗證；若 site key 是空的，前台不會出現驗證元件，結果是**所有人都登不進後台**。
2. **Web Analytics**：⚠️ `web/index.html` 的 beacon token 目前**與 paa-web 相同**，paa-ur 的流量會算進 paa-web 的統計。請在 Cloudflare Web Analytics 為本站另建 site，換上新 token。
3. **CSP**：目前是 `Content-Security-Policy-Report-Only`（只回報不阻擋，違規記在 Worker 日誌的 `[CSP-Report]`）。觀察一段時間無誤後改為 `Content-Security-Policy`。**`api/src/index.ts` 與 `build.mjs` 的 `writeHeaders()` 兩處要同步改**，內容字串也要一致。
4. **管理員密碼**：dev、prod 的臨時密碼首登後都要改。
5. **線上提問表單（目前停用）**：若決定在本後台處理諮詢，把 `api/src/index.ts` 的 `INQUIRY_FORM_ENABLED` 改成 `true`、`web/admin/admin.js` 的 `MODULES` 加回 `['inquiries', '線上諮詢']`。表單的人機驗證沿用第 1 項的 Turnstile；新提問的 Email 通知尚未實作。
6. **備份**：有正式內容後即應建立。`npm run backup:prod`（D1 dump ＋ R2 鏡像，輸出到 repo 外的 `../paa-ur-backup/`），需要 rclone 與 R2 唯讀 token。腳本的資源名稱直接讀 `wrangler.jsonc`；操作步驟目前參考 `docs/備份與還原手冊.md`（該文件仍是 paa-web 版本，名稱需自行對換）。

## 6. 網址：公會網站子路徑 /expand-life

本站不用獨立網域，掛在公會網站底下：

| 環境 | 網址 | 疊在哪個 Worker 前面 |
|---|---|---|
| prod | https://www.paa.org.tw/expand-life/ | paa-web 的 `paa-prod`（Custom Domain `www.paa.org.tw`） |
| dev | https://dev.paa.org.tw/expand-life/ | paa-web 的 `paa-dev`（Custom Domain `dev.paa.org.tw`） |

**運作方式**：`api/wrangler.jsonc` 的 `routes` 設 `www.paa.org.tw/expand-life*`（dev 為 `dev.paa.org.tw/expand-life*`）。
同一個 hostname 上，Cloudflare 先執行 Route 上的 Worker（本站），Custom Domain 上的 Worker（公會網站）視為 origin。
route pattern 只能以 `*` 結尾，所以也會比對到 `/expand-lifestyle` 這類路徑；`api/src/index.ts` 檔尾的 `fetch()` 會把不屬於 `/expand-life/…` 的請求原樣 `fetch()` 交回公會網站。

**前綴**：`/expand-life` 寫在 `api/src/base.ts`（說明改動時要同步的位置）。資料庫內容一律存不含前綴的站內路徑（`/files/…`、`/subsidy`），輸出時才補前綴。
build 產物在 `dist/expand-life/`，資產層看到的路徑就是實際網址。本機開 http://localhost:8787/expand-life/ 。

**同網域的注意事項**：
1. 根目錄的 `robots.txt` 屬於 paa-web，由它宣告 `Sitemap: https://www.paa.org.tw/expand-life/sitemap.xml` 並 `Disallow: /expand-life/admin`（paa-web 的 `api/src/index.ts`）。改前綴時要一起改。
2. 後台 cookie `paaur_admin` 的 Path 限縮在 `/expand-life/api/admin`，名稱也和公會網站的 `paa_admin` 不同，不會互相覆蓋。
3. 兩站同源：任何一邊出現 XSS 都能以登入者身分呼叫另一邊的後台 API（cookie Path／SameSite 擋不住同源的 JS），主要靠 CSP 防禦，CSP 從 Report-Only 轉正式時兩站都要顧到。
4. Turnstile 與公會網站共用同一個 widget（Hostnames 已含 `www.paa.org.tw`、`dev.paa.org.tw`），見 §4 第 1 項。Web Analytics 與公會網站共用同一個 token，以路徑區分。
5. prod 設 `workers_dev: false`；dev 保留 workers.dev（根目錄會導向 `/expand-life/`）。

**首次套用 Route 時先在 dev 驗證**：Cloudflare 文件只說 Route「優先於」同 hostname 的 Custom Domain，沒有明講可以疊在 Custom Domain 上。
`npm run deploy:dev` 後用 §3 的指令確認 `https://dev.paa.org.tw/expand-life/api/health` 回的是 `paa-ur-api`，且 `https://dev.paa.org.tw/` 仍是公會網站。
若不成立，備案是改由 paa-web 以 Service Binding 轉發 `/expand-life/*`。
